# Retro — 振り返りとルール資産への還元

**「同じ指摘を二度受けない」ための仕組み。** その場で直して終わりにせず、原因を分類して資産に変える。

## Process

### 1. 収集

今回のタスクから「手戻りの種」を集める:

- Reviewer（Codex等）の指摘事項（REQUEST_CHANGES の理由、APPROVE 時の Warning も含む）
- ユーザーからの訂正・差し戻し（「そうじゃなくて」「やり直して」等）
- lint / テスト / 型チェックで繰り返した修正
- タスクファイルの経緯メモ、`.claude/logs/cli-tools.jsonl`（あれば）

### 2. 分類

| 分類 | 例 | 還元先 |
|------|----|--------|
| **要件起因** | ACが曖昧で解釈がずれた、非ゴール漏れ | requirements スキルの質問改善 / AC の書き方を CLAUDE.md にメモ |
| **設計起因** | 軸の混在、レイヤー違反、ライブラリ誤用 | プロジェクトの rules / `.claude/docs/libraries/` |
| **実装イディオム** | エラーハンドリング・型・テストの流儀違反 | `lang-*` スキル（汎用なら plugin リポジトリに追記） |
| **プロセス逸脱** | 承認前に実装着手、レビュー省略 | orchestra スキル / hooks の改善提案 |
| **一度きり** | 再発可能性が低い個別事情 | retro ログに記録のみ |

### 3. 還元の判断ルール

- **汎用 vs プロジェクト固有を必ず判断する**（迷ったらユーザーに確認）
  - 汎用 → plugin リポジトリ（mac-initial-setting）の lang スキル等への追記を提案
  - 固有 → そのプロジェクトの CLAUDE.md / rules への追記を提案
- **同じ分類の指摘が2回以上**になったら「頻出」として、ルール化を強く推奨する
- ルールは増やしすぎない: 追記を提案する際、**代わりに削れる古いルールがないか**も確認する
  （ルール肥大はリマインダーの形骸化と同じ毒）

### 4. ユーザー承認 → 反映

提案を一覧で提示し、**承認されたものだけ**反映する:

```markdown
## Retro: {タスク名}

### 今回の手戻り（{N}件）
1. {指摘の要約} — 分類: {分類}

### ルール化の提案
- [ ] {提案1} → 還元先: {ファイル}
- [ ] {提案2} → 還元先: {ファイル}

### 記録のみ（一度きり）
- {事象}
```

### 5. 保存

retro ログを `.claude/docs/retro/{YYYY-MM-DD}-{タスク名}.md` に保存する。
次回の retro 時に過去ログを確認し、**再発していたら頻出昇格**させる。

## When NOT to

- 指摘ゼロでスムーズに終わったタスク（ログだけ残す価値もない）
- 振り返りのための振り返りはしない。提案が出ないなら「なし」で即終了
