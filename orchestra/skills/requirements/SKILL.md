# Requirements Definition

$ARGUMENTS の要件を「要件定義書」として成果物化する。

## 原則

**要件を会話の中に残さない。** 必ず以下の固定フォーマットの成果物に落とす。
以降の全工程（計画・テスト・レビュー・完了判定）はこのACを基準に行う。

## Process

### 1. 入力源の確認

- **口頭説明** → 質問で明確化（Step 2）
- **既存ドキュメント**（GitHub Issue、客先要件書、タスクファイル）→ 読んでACに変換し、不明点だけ質問
- **既存の要件定義書の変更** → 変更点を明示して再提示（AC番号は振り直さず、追加は AC-N+1、削除は取り消し線で履歴を残す）

### 2. 質問による明確化

brainstormingスキルの手法に従う:

- 一度に1つの質問、選択式を優先（`AskUserQuestion` ツール使用）
- 不明・曖昧な要件は推測せず、選択肢 + preview で比較提示
- 推奨オプションは先頭に置き「(Recommended)」を付ける

確認すべき項目:

1. **目的**: 何を達成したいか
2. **スコープ**: 含めるもの・除外するもの
3. **技術的要件**: 特定のライブラリ、制約
4. **成功基準**: 完了の判断基準

### 3. 要件定義書の作成（必須成果物）

```markdown
## 要件定義: {feature}

### 目的
{1-2文}

### 受け入れ条件 (Acceptance Criteria)
- **AC-1**: {Given/When/Then 形式。例: 未ログインのユーザーが購入ボタンを押したとき、ログイン画面にリダイレクトされる}
- **AC-2**: ...

### 非ゴール（やらないこと）
- {今回のスコープから明示的に除外するもの。最低1つ書く}

### 検証方法
| AC | 検証手段 |
|----|---------|
| AC-1 | unit test |
| AC-2 | 手動確認: {具体的なコマンド・手順} |
```

ルール:

- **各ACは単体で検証可能であること**。「使いやすくする」のような曖昧な表現はNG → 観測可能な振る舞いに直す
- **非ゴールを最低1つ書く**。実装レビューでのスコープクリープ検出はこれが基準になる
- **検証方法はこの時点で決める**。「手動確認」になったACが、実装後の動作確認の手順そのものになる
- ACの数の目安: 小タスクは1〜3個、通常機能は3〜7個。7個を超えたらタスク分割を提案する

### 4. ユーザー確認

要件定義書を提示し、「**このACが全て満たされたら完了、という認識で合っていますか？**」と確認する。
修正があればACを更新して再提示。**承認を得てから次工程へ進む。**

### 5. 永続化

- フロー（startproject / sin-task / para-task）から呼ばれた場合 → 呼び出し元の Persist 工程に従う
- 単体で使った場合 → CLAUDE.md の Workflow Conventions にタスクファイルの場所があればそこへ、
  なければ `docs/plans/{YYYY-MM-DD}-{feature}.md` に保存する

## このスキルがやらないこと

- 実装計画の作成（→ `plan` スキル / startproject Phase 2 後半）
- 要件の曖昧さレビュー（→ startproject Phase 3 で Reviewer が実施）
- 実装・テスト（→ 各フロースキル）
